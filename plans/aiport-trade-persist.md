## Исходный план (Planning)

Тип: bugfix воркера (`telegram-notify.js`). Деплой воркера — вручную пользователем.

## Симптом
В Telegram приходят сделки AI-портфеля (🤖 ПОКУПКА/ПРОДАЖА), которых нет в портфеле на сайте; пользователь «не помнит» покупки SAP. Это автономный вирт. портфель ИИ, но его состояние на сайте расходится с тем, что реально торгует воркер.

## Корневая причина (подтверждена кодом + SQL)
1. БД-триггер [supabase-ledger-guard.sql](../supabase-ledger-guard.sql) — `BEFORE UPDATE`. При `new_rev <= old_rev` он делает **`return OLD`**: строка молча остаётся старой, но PATCH всё равно отдаёт **204 OK**.
2. `writeRow` (telegram-notify.js) делает PATCH с `Prefer: return=minimal` и **не проверяет результат**. Значит rev-конфликт (клиент сохранил снапшот между чтением `fresh` и записью воркера) воркер НЕ замечает — изменения тихо откатываются.
3. `aiPortfolioRun` шлёт Telegram по каждой сделке **безусловно, после** `writeRow`. → уведомление уходит, даже если запись в `ledger` не закоммитилась.
4. `saveBak` пишет копию в `ai_state` (отдельная таблица, без guard — см. [ai-state.sql](../ai-state.sql)). Поэтому возможна устойчивая картина: `ledger` заморожен (write всё откатывается), `ai_state` уходит вперёд → воркер на след. циклах восстанавливается из `ai_state` (шлёт «♻️ ВОССТАНОВЛЕН») и торгует «теневой» копией, а сайт (читает `ledger`, [app.js:159](../app.js#L159)) показывает старое.

Худший случай: если таблица `ai_state` НЕ создана → `saveBak` тихо ничего не делает, и при rev-конфликте сделка теряется совсем (остаётся только в Telegram).

## Предусловие (проверить ПЕРВЫМ делом в Implementation)
Убедиться, что таблица `ai_state` создана в Supabase (выполнен `ai-state.sql`). Без неё durable-якоря нет. Диагностика: `?action=aiportstate` должен возвращать порт; если воркер часто шлёт «♻️ ВОССТАНОВЛЕН» — это маркер расхождения.

## Цели фикса
1. **Truthfulness:** Telegram-уведомление о сделке уходит ТОЛЬКО после durable-подтверждения записи (никаких фантомных сделок).
2. **No divergence:** `ledger.aiPort` реально догоняет состояние (сайт показывает сделку без открытия вкладки 🤖).
3. **Без регрессий** для прочих вызовов `writeRow`.

## Дизайн

### A. `writeRow` должен УМЕТЬ детектить коммит
`r.ok` недостаточно (триггер отдаёт 204 при откате). Решение: писать с `Prefer: return=representation`, прочитать вернувшуюся строку и сравнить `data.rev` с тем, что мы записали.
- Совпал `rev` → коммит прошёл (`return true`).
- Не совпал / строки нет → конфликт-откат (`return false`).
- Сохранить обратную совместимость: функция просто возвращает boolean; существующие вызовы, игнорирующие результат, не ломаются.

### B. Retry read-modify-write для aiPort
Хелпер (напр. `writeAiPortChecked(env, applyFn, {tries:3})`):
1. `loadRow` → текущий снапшот и его `rev` (=R).
2. `applyFn(snap)` — наложить наше состояние (`snap.aiPort = ap`, сохранив клиентские настройки из свежего снапшота; `snap.aiPortBak = ap`).
3. `rev = R+1`, PATCH с representation.
4. Коммит? да → success. нет → повтор с шага 1 (свежий R), до N раз, с небольшим backoff.

Конфликты по aiPort приходят не от клиента (клиент перенимает серверный aiPort — см. [pushState](../app.js#L31)), а от записи клиентом ДРУГИХ частей снапшота (вкладки и т.п.). Поэтому повторное наложение нашего `aiPort` на свежий снапшот безопасно.

### C. `aiPortfolioRun` — порядок: сначала durable, потом Telegram
1. Посчитать сделки (как сейчас).
2. **Durable-запись в `ai_state`** через `saveBak` + проверить `r.ok` (это якорь правды; `ai_state` без guard, коммитится надёжно).
3. Запись в `ledger` через retry-хелпер (B) — чтобы сайт показал без вкладки 🤖.
4. **Telegram — только если durable-запись (шаг 2) подтверждена.** Если не подтверждена → НЕ слать сделки; один раз отправить админ-сообщение «цикл не удалось сохранить» (для наблюдаемости). Сами сделки подтянутся примирением (`aiPortAuthoritative`) на след. цикле/вкладке.

### D. `saveBak` — проверять успех
Сейчас тоже без проверки `r.ok`. Вернуть boolean, использовать в шаге C.2.
