## A. Надёжность AI-вызовов (worker#4, остаток)

**Проблема (проверено 2026-09-10).** Четыре пути к Anthropic идут «сырым» `fetch` без повторов: `anthropicRound` (SSE, но без таймаута, `telegram-notify.js:148`), `aiChat` (:1382), `aiPortfolioRun` (:1732), `portfolioAnalyze` (:1997). При 429/529 цикл AI-портфеля и анализ портфеля падают — теперь это хотя бы видно в Workers Logs (S8), но цикл пропускается. `stop_reason: max_tokens` нигде не проверяется: у aiport/pfanalyze (json_schema, `max_tokens` 6000 при adaptive thinking) усечённый JSON молча превращается в «0 сделок» и фиксирует `lastRunAt`. `ai_jobs` знает только `done`/`error` — при гибели изолята задача «висит» до таймаута клиента. `?action=aiport`/`pfanalyze` считают внутри `streamJson` вне `ctx.waitUntil` — обрыв клиента может прервать цикл между `saveBak` и записью ledger.

**Сделать:**
1. `anthropicRound`: `AbortController` с бюджетом `AI_ROUND_MS` (≈ 4 мин) — зависший стрим бросает ошибку с пометкой `timeout` (её уже ретраит `anthropicRun`).
2. `aiChat`, `aiPortfolioRun`, `portfolioAnalyze` → через `anthropicRun` (повторы 429/5xx/529 с бэкоффом, общий разбор usage). `anthropicRun` возвращает и `stop_reason` последнего раунда.
3. `max_tokens`: если `stop_reason === 'max_tokens'` у json_schema-вызова — один повтор с `max_tokens × 1.5` (потолок `AI_MAX_TOKENS_CAP`); не помогло — ошибка «ответ модели усечён», **`lastRunAt`/`pfAnalysisAt` не ставятся** (следующий тик повторит), в лог.
4. `ai_jobs`: писать `running` при старте (`aiJobStart`), клиент показывает «идёт…» вместо немого ожидания; таймаут клиента не меняется.
5. `?action=aiport` и `?action=pfanalyze`: работа в `ctx.waitUntil`, стрим только ждёт её промис (обрыв клиента не прерывает запись).

**Тесты (worker-suite):** чистые хелперы — `aiRetryable(status, msg)`, `aiNeedsMoreTokens(stop_reason, schema)`, бюджет повторов; мок `fetch` для `anthropicRun`: 529 → повтор → успех; `max_tokens` → один повтор с большим лимитом; второй `max_tokens` → ошибка без записи гейта. Сквозной прогон `aiPortfolioRun` в node с подменённым fetch (как bookcheck в S8).

**Проверка вживую:** после деплоя — `?action=aiport` (кнопка ▶) и `pfanalyze` отрабатывают; в Workers Logs нет `упал`.

## B. Экранирование внешнего текста и CSP (security-rbac#6 остаток, #7)

**Состояние.** В S8 появились глобальные `escHtml`/`safeUrl` (app.js), закрыты новости и e-mail в «Доступе». Остались: 6 локальных `esc` с разной семантикой (`app.js:427, 2933, 2996`, `app-5.js:561`, `app-2.js:1229` — это экранирование для JS-строк в `onclick`, `chart.js:130`); имена компаний из Yahoo `?profile=` (пишутся в `r[1]`, уходят в `shared_analysis`) выводятся без экранирования — `app-2.js:204, 543`, `app-3.js:842, 1185`, `app-4.js:489` и др.; `app.js:2933` падает на не-строке (`s.replace` без `String()`).

**Сделать:**
1. Инвентаризация: `grep` всех `${…name…}`, `${…title…}`, `${…note…}`, `${…publisher…}` в шаблонах `innerHTML` — список в итогах сессии.
2. Все HTML-локальные `esc` → `escHtml` (кавычки тоже); `app-2.js:1229` переименовать в `escJs` (строка внутри `onclick='…'`) и оставить; `desk.js` уже на `dkEsc` (= escHtml) — не трогать.
3. Источник: `pf3FillProfile` — имя из Yahoo хранить как есть, экранировать на выводе (не портить данные).
4. CSP через `<meta http-equiv>` (Q3): `object-src 'none'; base-uri 'self'; img-src 'self' data: https:; connect-src` — явный список (Supabase, воркер, frankfurter.dev, open.er-api.com, finnhub, jsdelivr для LWC). `script-src` пока с `'unsafe-inline'` — без него не работают 148 inline-обработчиков (ux-ia#13, S7b). `frame-ancestors` в `<meta>` не действует — отметить, что нужен заголовок хостинга (GitHub Pages не даёт).

**Тесты (app-suite):** `escHtml`/`escJs` на кавычках и не-строках; снапшот-тест «имя с `<img onerror>` в строке портфеля → в HTML списка/карточки/дивидендов нет тега» для 3–4 рендереров. Живая проверка: headless Chrome, все 5 экранов Trade Desk и классика без ошибок CSP в консоли.
