# Функциональные регрессионные тесты

Цель — при добавлении новых фич не ломать старые. Тесты гоняют **реальные
функции** из `app.js` и `telegram-notify.js` (а не их копии), поэтому ловят
регрессии в самой логике.

## Запуск

```bash
bash tests/run.sh
```

Выход `0` — всё зелёное; `1` — есть падения. Сьют (`app` / `worker`) считается
упавшим, если ЛЮБОЕ из:

- код возврата раннера ≠ 0 (142 — таймаут 90 с, 127 — нет `osascript`/`perl`,
  иное — крэш);
- в выводе нет строки-маркера `APP TESTS: N/N passed` / `WORKER TESTS: N/N passed`
  (пустой вывод, крэш раннера до сводки);
- в выводе есть `FAILED`, `EVAL <suite>` (исходник не загрузился) или
  `execution error` (крэш JXA);
- число кейсов `N` (второе число маркера) ниже порога — `MIN_CASES_app=420`,
  `MIN_CASES_worker=70` в начале `run.sh` (защита от случайно урезанного файла
  кейсов; поднимать вместе с ростом кейсов).

Каждая причина печатается отдельной строкой `❌ <suite>: <причина>`.
**Запускать перед каждым коммитом новой фичи.**

## Как устроено

Внешнего фреймворка/npm нет. Раннеры (`run-app.js`, `run-worker.js`) — это
скрипты для `osascript -l JavaScript` (движок JavaScriptCore):

1. поднимают минимальные заглушки браузерного окружения (`document`, `window`,
   `localStorage`, `fetch`, `crypto`, `supabase` … — общий файл `env-stubs.js`,
   его же грузит стенд копии ledger) и `ALL`;
2. читают реальный исходник, убирают авто-`boot()` (app) / `export default`
   (worker);
3. `eval`-ят исходник (для app — `signals.js` + `app*.js` в порядке `index.html`,
   плюс фикстура свечей `fixtures-signals.js`) вместе с кейсами в одном scope — кейсы видят настоящие
   функции и глобалы;
4. собирают результаты в `__res` и печатают сводку.

Кейсы — в `cases-app.js` и `cases-worker.js`.

JSC в `osascript` не крутит промисы, поэтому асинхронные пути воркера (вызовы
Claude с повторами/таймаутами, сквозной цикл AI-портфеля, роуты с `waitUntil`)
проверяет третий сьют — **`run-worker-async.js` под node** (`node tests/run-worker-async.js`,
маркер `WORKER-ASYNC TESTS: N/N passed`, порог `MIN_CASES_worker_async`). Он грузит
воркер в `vm`-контекст с подменёнными `fetch` (Anthropic SSE / Supabase / Yahoo /
Telegram) и `Date` (среда, биржи открыты — тест не зависит от дня запуска). Без node
`run.sh` падает, а не пропускает сьют.

Четвёртый сьют — **`run-sync-sim.js` под node** (E4, `plans/ledger-model-e.md` §4.E4; маркер `SYNC-SIM TESTS: N/N passed`,
порог `MIN_CASES_sync_sim`): сквозная симуляция синка клиента. Два клиента — `vm`-контексты с настоящим кодом сайта
(скрипты из `index.html` + `env-stubs.js`), фейковый Supabase — одна строка `ledger_state` с триггером
`supabase-ledger-guard.sql` (не выросший rev → строка остаётся, событие всё равно уходит), realtime-рассылка (в т.ч. «строка
больше лимита» — событие без `data`), задержки сети, офлайн (`navigator.onLine=false`), `flaky` (сеть есть, запросы падают),
`failPut` (запись не дошла), «потерянный ответ» (запись прошла, ответ — ошибка), «воркер»
(как `writeRow`). Часы общие и управляемые (`clock.run(ms)`: таймеры клиентов, задержки и realtime + прогон микрозадач).
Сценарии: разные единицы на двух устройствах, одна позиция (тост), воркер при стоящем таймере, офлайн → онлайн, потерянный
ответ (кэш не удваивается), четыре отказа подряд (прежний тост), котировки на обоих + сделка, удаление/добавление сделок,
правка во время push, потерянный ответ с повторным push тем же rev, офлайн-правка при неизменном облаке, `pullState` во время push, сделка по одной бумаге на обоих, офлайн-сделка при облаке на +2 rev, две покупки на одну сумму + AI-прогон на каждом, потерянный ответ без коммита (тост «сверьте позицию»), подряд не дошедшие записи (память очереди), fail-closed чтения aiPort. В каждом — оба клиента = облако, их `stateRev` и база слияния = облако, очередь синка пуста.
Отладка: `--only=<подстрока>`, `--verbose` (предупреждения клиентов), `SIM_TRACE=1` (записи и доставки realtime).

## Стенд копии ledger (вне `run.sh`)

`node tests/ledger-copy.js <copy.json | --bundle> [--ref=<git ref>] [--expect-drop=…] [--expect-add=…] [--loose] [--ai-out]`

— «проверка на копии» блока E (`plans/ledger-model-e.md` §4.E0 п.4, §5). Грузит клиентские скрипты
из `index.html` в node `vm` с `env-stubs.js` дважды — рабочее дерево и `--ref` (через `git show`), —
делает `applyRemoteState(копия)` → `snapshotState()` и сравнивает: I0 снапшот (кроме ожидаемых путей,
`data.*.count` — шаблон), I1 первичные факты (строки tk/qty/buy/ccy/price, cashFree, сделки, posMeta, план…),
I2 идемпотентность, I3 контракт префикса строк (для E2), I4 размер и запас до лимита realtime 1024 КБ.
Копия — личные данные, лежит вне репозитория (`~/dash-ledger-copies/`); `--bundle` — самопроверка на `data.js`.

`--merge-sim` (E4): вместо I0–I5 — сценарии `run-sync-sim.js` на копии как исходной строке облака
(`node tests/ledger-copy.js <copy.json> --merge-sim`; то же — `node tests/run-sync-sim.js --copy=<copy.json>`).

`--ai-out` (E5, `plans/ai-reports-e5.md` §7): в HEAD после `applyRemoteState` — перенос AI-отчётов «как будто сервер подтвердил всё» (`aiLedgerExtract` → `aiLedgerStrip`). **I5** — извлечено ровно всё (независимый подсчёт по видам и вкладкам, каждая запись глубоко равна исходной, `bad` перечислены); к `--expect-drop` сами добавляются `stockAiLog` и `data.*.aiHistory/aiReport/analysis/analysisHistory`.

## Паритет клиент ↔ воркер (`fixtures-parity.js`)

Общая фикстура обоих JSC-сьютов (раннеры подключают её перед кейсами): контракт строки v3-вкладки E2 — `RC`, `COLN`,
`COLN_RE` и раскладки заголовков реальных вкладок с ожидаемыми индексами. `parityRun(suite, RC, COLN, COLN_RE, colOf)`
сверяет объявления своего сьюта с таблицей — отставшая копия (клиент или воркер) ломает свой сьют.

## Как добавить тест

В `cases-app.js` / `cases-worker.js` добавь группу:

```js
grp('моя фича', function(){
  __eq('что проверяю', myFunc(вход), ожидание);     // строгое равенство (JSON)
  __approx('число ~', myFunc(x), 16, 0.01);          // с допуском
  __ok('булево', condition);
});
```

Группа изолирована: исключение внутри `grp` не валит остальные тесты, а
отмечается как FAIL.

## Pre-commit hook (авто-блок коммита при красных тестах)

В репозитории лежит `.githooks/pre-commit`. Он гоняет тесты, если в коммите
затронуты `app.js`, `app-2.js`…`app-5.js`, `telegram-notify.js` или `tests/`
(регэксп `^(app(-[0-9]+)?\.js|telegram-notify\.js|tests/)`), и **блокирует
коммит** при падении.

Активировать после клона (один раз — `core.hooksPath` хранится локально):

```bash
git config core.hooksPath .githooks
```

Обойти в крайнем случае: `git commit --no-verify`.

## Совет

При добавлении новой фичи с расчётами/состоянием — сразу пиши на неё кейс
(особенно если она пишет в синк: добавь ключ в проверку `snapshotState keys`).
